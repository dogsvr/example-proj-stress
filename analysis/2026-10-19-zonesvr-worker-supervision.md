**术语**

- **槽位（slot）**：dogsvr 的 worker 位置，zonesvr 配置 `workerThreadNum: 2`，即槽 0、槽 1。
- **候选（candidate）**：热更新时为某个槽位新建、尚未接管的 worker。
- **在途数**：主线程已派出、尚未收到回包的请求数（指标 `dogsvr_worker_pending`）。
- **rolling / allAtOnce**：两种热更新策略。rolling 逐个槽位"建候选 → 等就绪 → 接管 → 排空旧 worker"；allAtOnce 一次建好所有候选，全部就绪才一起接管。
- **SAB 通道**：主线程与 worker 之间基于 SharedArrayBuffer 的环形缓冲通道（10-17 文档 §七）。
- **场景 F / B / D**：`example-proj-stress/bots` 的压测场景：F 为在线会话混合（本文只查排行榜，cmd 20004），B 为登录后循环打对战，D 为 B 的负载加一次 zonesvr 热更新。

**测试分三层**

1. dogsvr 单元测试：新增 12 个用例，见 §四.1。
2. 真实进程故障注入：新增测试专用工具 [`chaos/`](../chaos/README.md)，见 §四.2 ~ §四.7。它包含一个包装真实 `zonesvr_logic.js` 的 worker 入口：按槽位读取 `/tmp/dogsvr-chaos/` 下的标记文件来注入"加载失败 / init 抛错 / init 挂起 / 就绪后退出"，并把每个 worker 的加载、就绪、退出时间写入事件文件；另有一个编排脚本 `run_supervision.py`。
3. 压测：稳态性能与 10-17 对比（§二）；热更新期间的新旧版本对照（§三）；反复创建 worker 的内存（§四.8）。

## 三、热更新期间：新旧版本对照

### 3.1 方法

- **负载与触发**：与 §二 相同的 F 1000 负载、原始配置，在 bot 启动后 120 s 和 210 s 各执行一次 `pm2 trigger exp-zonesvr hotUpdate`（rolling 策略，即默认策略）。
- **版本**：
  - 新版为 `a762c3d`。
  - 旧版为 `32d84b8`，即 10-17 文档测的 lb fix 版本。用 `git archive` 解到 `/tmp` 构建后，临时替换 `dogsvr/dist`。logger、cl-*、example-proj 都通过软链接用这份 dist。替换前后用 `dist/main_thread/server_core.js` 的 sha256 校验：旧 `ad6a0ce0…`，新 `058d071f…`。
- **重复次数**：每个版本各跑 1 次，每次含 2 次热更新。
- **指标**：服务端 `dogsvr_cmd_duration_milliseconds` 直方图按 5 s 步长取差，再算每个窗口内耗时 > 500 / > 1000 ms 的请求数。稳态下两版都没有超过 500 ms 的请求（附录 C.2），所以这个计数对热更新造成的慢请求很敏感。

### 3.2 结果

| 指标 | 旧版 32d84b8（第 1 / 2 次） | 新版 a762c3d（第 1 / 2 次） |
|---|---:|---:|
| 失败数 / 事务超时 | 0 / 0 | 0 / 0 |
| 含触发时刻的 5 s 窗口内耗时 > 500 ms 的请求 | **894 / 850** | **0 / 0** |
| 其中 > 1000 ms | 0 / 0 | 0 / 0 |
| 该窗口吞吐（与前一个 5 s 窗口相比） | 17756 → 14499（−18.3 %） / 17658 → 14502（−17.9 %） | 17885 → 16625（−7.0 %） / 17486 → 16025（−8.4 %） |
| `pm2 trigger` 耗时 | 0.53 / 0.52 s | 1.60 / 1.68 s |
| 槽 0、槽 1 完成替换（相对触发） | 331 / 517 ms；325 / 512 ms | 870 / 1584 ms；927 / 1665 ms |
| 旧 worker 退出方式 | 全部"正常排空"（drained gracefully） | 全部"正常排空"（drained gracefully） |
| 进程启动到开始监听 | 15 ms | 527 ms（本轮其他无故障或快速失败的重启为 452 ~ 554 ms） |

解读：

- **旧版**：先装上新 worker、再等它初始化。新 worker 初始化的约 0.5 s 里，leastLoad 按在途数 0 优先向它派发请求，这些请求在 SAB 环里等到初始化完成才处理，于是落到 > 500 ms 桶里。这是按代码顺序做的推断，未逐条核对 894 个请求的去向。
- **新版**：等候选就绪再接管，没有这段等待。代价是每个槽位多等一次初始化（约 0.5 s），两个槽位串行，热更新整体慢约 1 s。
- **吞吐下降（−7 % / −8 %）**：新版两次运行里都观察到，推测来自候选初始化（加载模块、建连接）占用的 CPU 和新 worker 冷启动，未单独验证。
- **启动**：新版的 `startServer()` 等所有槽位第一次初始化有结果后才开始监听，因此启动多出约 0.5 s，但开始监听时 worker 已能处理请求。

### 4.2 L-A：服务中的 worker 崩溃（F 1000，约 360 s）

用故障注入让槽 0 的 worker 以 `process.exit(9)` 退出：先连续三次（每次在上一次恢复后 10 s），然后间隔 70 s 再一次；最后槽 0、槽 1 同时退出。

| 步骤 | 重启间隔（日志） | 失败数 / 崩溃前在途 | 恢复耗时（退出 → 新 worker 就绪） | 恢复后 |
|---|---:|---:|---:|---|
| A1 | 1000 ms | 475 / 488 | 1522 ms | 下一次崩溃在 10 s 后，不单独评估 |
| A2 | 2000 ms | 461 / 476 | 2538 ms | 同上 |
| A3 | 4000 ms | 445 / 388（A2 之后两侧尚未平衡） | 4539 ms | 吞吐 2859 → 3476 /s；45 s 后两侧在途 424 / 425 |
| A4（间隔 70 s） | 1000 ms（稳定 60 s 后清零） | 426 / 424 | 1512 ms | 吞吐 3454 → 3490 /s；在途 438 / 438 |
| A5（两槽同时） | 各 1000 ms | 4409 / 883 | 1513 / 1524 ms | 吞吐 3438 → 3471 /s；在途 431 / 431 |

- **在途请求**：每次崩溃都在退出时立即失败，错误信息为 `worker exited|exitCode:9`；同期另一个槽位照常服务。
- **A5 两槽同时空置的约 1.5 s**：4409 个失败中有 3086 个落在 ≤ 0.5 ms 桶，即 `no available worker` 立即失败；其余 1323 个耗时在 0.5 ms 以上，崩溃前两侧在途合计 883，其余未逐一归因；没有失败耗时 ≥ 2 s。bot 连续失败 3 次后会断线重连，这段时间的重连登录也立即失败（cmd 20001 失败 1753 次，全部出现在 A5 之后的同一个 5 s 采样点），但所有 bot 都在退避窗口内重连成功，没有永久退出。
- **全程不变量**：事务超时 0；日志 `no callback for txnId` 0；zonesvr 进程 pid 和 pm2 重启次数不变；bot 停止后在途归零；线程数 17 → 17。
- **交叉核对**：服务端排行榜查询失败 4442 次，bot 日志的操作失败 4452 次，相差 0.2 %。
- **报告与检查项**：
  - 本节数据来自 `2026-10-19T03-03-supervision-crash`，28 / 28 通过。
  - 首轮（`2026-10-18T14-09-supervision-crash`）行为一致，但有 4 项检查 FAIL，都出在检查写法上：其中 2 项是吞吐统计窗口与下一次崩溃重叠，另外 2 项撞上测量问题 M1、M2（§五.4）。已修正检查后重跑。

- **dir 热更新**：两个槽依次替换，旧 worker 均正常排空；dir 在主线程监听 HTTP，不受影响。
- **battlesvr 热更新**：

### 4.8 反复创建 worker 的内存（spawn soak）

F 200 负载下每 15 s 一次 rolling 热更新，共 20 次（每次创建 2 个 worker，共 40 个），每 5 s 采样 `/proc/<pid>/status`。对照组按同一时间线运行，但不触发热更新。

| 运行 | 热更新前（35 ~ 45 s） | 最后一次热更新后（负载中） | 继续负载 180 s 后 | 停负载后 |
|---|---:|---:|---:|---:|
| soak #1 | 866 MB | 1421 MB | —（没有延长） | 约 30 s 后 917 MB |
| soak #2（延长 180 s 负载） | 885 MB | 约 1427 MB | 1437 ~ 1439 MB | 约 1.7 min 后仍 1454 MB；约 2.6 min 后 771 ~ 780 MB |
| 对照组（不热更新） | 862 MB | 927 MB | — | 928 MB |

- **增量**：负载持续时，每创建一个 worker，RSS 约增加 12 MB：soak #1 共增加 555 MB，扣除对照组同期的 65 MB 后除以 40 个 worker。
- **回收时机**：负载期间不回收，soak #2 又观察了 180 s，RSS 持平；停负载后 0.5 ~ 2.6 min 回落到基线或更低。所以不是永久泄漏。
- **原因（推断）**：可能是 V8 只在进程空闲时才做的完整回收，收走了与旧 worker 相关的对象（含 SAB 后备内存）；未验证。
- **风险**：持续有流量且 worker 反复重启时（例如某个槽位在流量下崩溃循环，按 60 s 封顶约每分钟 1 次），RSS 会持续增长到流量下降为止。
- **代码审查推测的泄漏（问题 6）未得到证实**：推测的机制是日志 SAB 从不解除挂载、退出 worker 的读端一直等在 `Atomics.waitAsync` 上，每个 worker 残留约 6 MB。若确实泄漏，40 个 worker 应在空闲后留下上百 MB，实测空闲 RSS 与对照组持平。
- **不同代码版本**：旧版没有做同样的实验；热更新创建 worker 的路径在 `a762c3d` 之前就存在。
- VmSize 不能用来判断泄漏，见测量问题 M6。
- 三次运行都是 0 失败、线程数 17 → 17。

### 5.2 可优化项（待决策）

| # | 问题 | 位置 | 证据 |
|---|---|---|---|
| 2 | rolling 中止后版本混杂：失败槽之前的槽位已换成新代码并保持下去，直到下一次热更新或重启；README 写的是 "the update aborts and the old workers keep serving"；中止回复只有 `aborted at slot N`，不说哪些槽位已换成新代码，也不含 init 失败原因（只在日志里） | `hot_update.ts` RollingStrategy | 单元用例、L-C4（槽 0 v3 / 槽 1 v2，混杂保持了约 40 s，直到下一次触发） |

这一项是"rolling 本该如何收尾"的设计选择，暂不定性为缺陷，留待以后判断。判断时需要的事实：

- **只有槽 0 成功、后面的槽位失败才会混杂**。所有槽位都会遇到的失败在槽 0 就中止，不会混杂（L-C2 配置改坏、L-C3 Redis 不可达都是如此）。会混杂的是只影响个别槽位的失败，例如候选初始化时恰好遇到依赖抖动或超过 `workerInitTimeout`。
- **影响**：
  - leastLoad 没有会话亲和，同一玩家的相邻请求可能分别落到新旧代码上；改动涉及数据格式或协议时有不一致风险。
  - 运维从回复和 README 看不出槽 0 已经换了。
  - 留在旧代码上的槽位一旦崩溃，会从磁盘加载新代码（问题 10）。
- **旧代码已不在磁盘上**：热更新前 `npm run build` 已覆盖 dist，旧代码只在旧 worker 的内存里。要在中止后恢复成全旧，只能让已替换槽位的旧 worker 活到所有槽位都成功为止。
- **成功的 rolling 本身也有短暂混杂**：从槽 0 接管到槽 1 接管，按 §三 新版日志推算约 0.7 s。allAtOnce 才是全有或全无：所有候选就绪后同时接管，任何一个失败就全部丢弃（L-D2 验证），代价是热更新期间 worker 数临时翻倍。

候选方案：

| 方案 | 要改的地方 | 代价 |
|---|---|---|
| A. 视为 rolling 的固有语义（"逐个替换，失败就停在当前位置"） | README 如实描述，并指出要全有或全无就用 allAtOnce；中止回复写明已换成新代码的槽位和失败原因 | 只改文档和报错文案 |
| B. 中止后必须恢复全旧 | rolling 改为替换过的旧 worker 不退出，全部成功后再统一排空，失败时切回 | 热更新期间每个槽位新旧并存，内存峰值与 allAtOnce 相同；rolling 与 allAtOnce 的区别只剩初始化串行还是并行 |
| C. 默认策略改为 allAtOnce | `hotUpdateStrategy` 默认值与文档 | 每次热更新 worker 数临时翻倍（zonesvr 为 4 个，rolling 最多 3 个） |

单元用例 `rolling abort at slot 1 leaves slot 0 on the new code` 固定的是当前行为，先保留；若以后选 B，需要把它改成期望槽 0 仍是旧 worker。

### C.2 取数方法

- **稳态**：`python3 analysis/scripts/zonesvr_run_stats.py prom|pyro reports/2026-10-18T13-33-f_realistic_session reports/2026-10-18T13-39-f_realistic_session`。
- **逻辑与热更新用例**：`python3 chaos/run_supervision.py <case>`，用法见 [`chaos/README.md`](../chaos/README.md)。每个报告目录里有：
  - `summary.md`：逐项 PASS / FAIL 和实测值；
  - `data.json`：全部原始数值；
  - `events.ndjson`：故障注入 worker 的事件；
  - `bots-*.log`：bot 输出。
- **计数器差值**：用 `sum(last_over_time(<sel>[15s]))` 在两个时刻求差，不用 `increase()`，因为后者会漏掉新出现序列的第一个点。zonesvr 的主线程指标不带 pid 标签，重启后 15 s 内会读到旧进程的值，所以用例在重启后先等 20 s 再取基线；启动类用例改用新进程的累计值。
- **热更新慢请求**：`query_range` 步长 5 s，对 `dogsvr_cmd_duration_milliseconds_bucket{svr="zonesvr",cmdId="20004",ok="1",le="500"|"1000"}` 与 `_count` 逐步取差。稳态时 le=200 桶外的请求都在 (200, 500] 桶内，> 500 ms 为 0。
- **失败数**：以服务端 `dogsvr_cmd_duration_milliseconds_count{ok="0"}` 为准（M2、M3），bot 侧用日志中的 `"bot op failed"` 行数交叉核对。
